> 작성 기준일: 2026-06-20 (Phase 6 완료 시점)  
> 목적: 개인 개발 기록 + 포트폴리오 공개

## 1. 제품 개요

**Monimo**는 "엑셀 없이, 수식 없이 — 하루 5분으로 쓰는 개인 웹 가계부"다.

가계부를 시작하고 싶지만 엑셀은 복잡하고, 기존 앱은 기능이 많아 오히려 진입 장벽이 높은 사람을 위한 미니멀 가계부 웹 앱이다. 수입·지출을 빠르게 기록하고, 카테고리별로 분류하고, 월별 흐름을 한눈에 파악하는 것이 핵심이다.

| 항목          | 내용                                 |
| ------------- | ------------------------------------ |
| 앱 이름       | Monimo                               |
| 카테고리      | 개인 금융 / 가계부                   |
| 플랫폼        | 웹 (데스크톱 최적화, MVP)            |
| 아키텍처      | 멀티유저 SaaS (사용자별 데이터 격리) |
| 출시 목표     | 2026년 7월                           |
| 비즈니스 모델 | 미정 (현재 무료 운영, 향후 검토)     |

## 2. 타겟 사용자 & 문제 정의

### 타겟 페르소나

**"처음 가계부를 시작하는 누구나"**

- 사회초년생, 지출 관리를 처음 시도하는 사람
- 가계부 앱을 써봤지만 기능이 많아 포기한 경험이 있는 사람
- 엑셀로 가계부를 만들다가 수식 관리에 지쳐 그만둔 사람

### Pain Points

| 문제                               | 기존 대안           | Monimo 접근                 |
| ---------------------------------- | ------------------- | --------------------------- |
| 엑셀은 수식·서식 관리가 번거롭다   | 직접 수식 작성 필요 | 입력만 하면 자동 집계       |
| 토스·뱅크샐러드는 기능이 너무 많다 | 60+ 메뉴, 자동 연동 | 핵심 기능만, 수동 입력 중심 |
| 앱 설치가 귀찮다                   | iOS/Android 앱      | 웹 브라우저에서 바로 사용   |
| 카테고리 분류가 복잡하다           | 직접 설정 필요      | 프리셋 13개 기본 제공       |

## 3. 기능 요구사항

### v1 완료 기능 (Phase 1–6)

#### 인증

- 이메일 + 비밀번호 회원가입 (이메일 인증 필수)
- 로그인 / 로그아웃
- 비밀번호 강도 검증 (8자 이상, 숫자·특수문자 포함)
- 멀티유저: RLS로 사용자별 데이터 완전 격리

#### 거래 관리

- 수입 / 지출 등록 (금액, 카테고리, 날짜, 계좌, 메모)
- 거래 수정 / 삭제 (슬라이드 패널 UX)
- 월별 거래 목록 (날짜 그룹 + 일별 소계)
- 필터: 거래 유형 (전체/지출/수입/이체), 계좌, 카테고리
- 월 네비게이션 (이전달/다음달)

#### 이체 관리

- 계좌 간 이체 등록 (출금 계좌, 입금 계좌, 금액, 날짜, 메모)
- 이체는 수입/지출 합산에서 완전 분리

#### 계좌 관리

- 계좌 등록: 이름, 타입 (입출금/신용카드/저축적금/현금), 색상, 초기 잔액
- 계좌 편집 / 소프트 삭제
- 잔액 실시간 계산: `초기잔액 + 수입 − 지출 + 이체입금 − 이체출금`
- 순자산 헤더 (총 자산 / 총 부채 / 순자산)
- 계좌 상세 패널: 월별 거래·이체 타임라인

#### 카테고리 관리

- 프리셋 13개 기본 제공 (지출 10 + 수입 3), 삭제 불가
- 커스텀 카테고리 추가 (이름 + 이모지 + 지출/수입 구분)
- 카테고리 삭제 시 해당 거래는 "기타"로 자동 이동

#### 레이아웃

- 사이드바 (232px): 새 거래 추가 버튼, 네비게이션, 사용자 프로필
- 월별 요약 카드: 수입, 지출, 잔여 예산, 순자산 변화
- 계좌 미보유 시 거래 추가 차단 + 안내 모달

## 4. 핵심 설계 결정사항

단순 기능 나열이 아닌, **왜 이렇게 만들었는가**를 기록한 섹션이다. 각 결정은 채택한 방식, 버린 대안, 선택 근거를 포함한다.

### 결정 1: 계좌 잔액 — 실시간 계산 vs DB 저장

|          | 내용                                                                                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **채택** | 실시간 계산 (클라이언트에서 accounts + transactions + transfers 집계)                                                                                                                                        |
| **버림** | DB에 `balance` 컬럼을 두고 거래 발생마다 업데이트                                                                                                                                                            |
| **근거** | Supabase는 트랜잭션 원자성을 클라이언트에서 보장하기 어렵다. 거래 INSERT와 balance UPDATE가 따로 실행되면 불일치가 발생할 수 있다. 실시간 계산은 항상 정확하고, MVP 규모(수백~수천 건)에서 성능 차이가 없다. |

```
실제 공식: initial_balance + Σ(수입) − Σ(지출) + Σ(이체입금) − Σ(이체출금)
신용카드: initial_balance를 음수로 저장 → 부채로 자동 처리
```

### 결정 2: 이체 데이터 구조 — 독립 테이블 vs transactions 타입 추가

|          | 내용                                                                                                                                                                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **채택** | 독립 `transfers` 테이블 (from_account_id, to_account_id, amount, date)                                                                                                                                                                                      |
| **버림** | `transactions.type = 'transfer'`로 처리, 출금·입금 레코드 쌍으로 관리                                                                                                                                                                                       |
| **근거** | 이체는 수입/지출 합산에서 완전히 분리되어야 한다. transactions에 이체를 넣으면 집계 시 `WHERE type != 'transfer'` 조건을 모든 쿼리에 추가해야 하고, 출금·입금 두 레코드의 일관성을 수동으로 유지해야 한다. 독립 테이블은 집계와 이체를 구조적으로 분리한다. |

### 결정 3: 계좌 삭제 — 소프트 삭제 vs 하드 삭제

|          | 내용                                                                                                                                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **채택** | 소프트 삭제 (`is_active = false`), 연결 거래 데이터 보존                                                                                                                                                                                           |
| **버림** | 하드 삭제, 연결 거래도 함께 삭제 또는 NULL 처리                                                                                                                                                                                                    |
| **근거** | 계좌를 삭제해도 과거 거래 기록은 유지되어야 한다. 하드 삭제 시 히스토리 손실 위험이 있고, NULL 처리된 거래는 집계 오류를 낼 수 있다. 소프트 삭제는 데이터 무결성을 보장하면서 UI에서만 숨긴다. 단, 연결된 거래가 있는 계좌는 삭제를 아예 차단한다. |

### 결정 4: 카테고리 프리셋 — 공용 레코드 vs 사용자별 복사

|          | 내용                                                                                                                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **채택** | `categories.user_id = NULL`인 공용 레코드, RLS에서 `user_id IS NULL` 허용                                                                                                                                                     |
| **버림** | 회원가입 시 프리셋을 사용자별로 복사하여 각자 보유                                                                                                                                                                            |
| **근거** | 사용자별 복사는 DB 레코드 수를 사용자 수 × 13배로 불필요하게 증가시킨다. 공용 레코드는 스토리지를 절약하고, 프리셋 수정 시 전체 사용자에게 즉시 반영된다. 다만 프리셋은 수정·삭제 불가(UI 레벨에서 차단)로 안전성을 확보한다. |

### 결정 5: 계좌 미보유 시 거래 추가 UX

|          | 내용                                                                                                                                                                                                                                                                       |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **채택** | 안내 모달 팝업 (계좌 등록하러 가기 / 취소)                                                                                                                                                                                                                                 |
| **버림** | 자동 리다이렉트, 또는 거래 폼 모달 내 인라인 경고                                                                                                                                                                                                                          |
| **근거** | 자동 리다이렉트는 사용자가 이동 이유를 읽기 전에 화면이 바뀐다. 인라인 경고는 사용자가 능동적으로 확인해야 하고, 계좌 없이 폼을 완성할 수 없어 UX가 어색하다. 안내 모달은 선택권을 제공하고, 취소 시 현재 페이지를 유지한다. 변경 범위도 `AppLayout.jsx`만으로 최소화했다. |

### 결정 6: 상태 관리 — Context API vs 전용 라이브러리

|          | 내용                                                                                                                                                                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **채택** | Context API 최소 활용 (AuthContext, LedgerRefreshContext 2개)                                                                                                                                                                                                                     |
| **버림** | Redux, Zustand 등 전용 상태 관리 라이브러리                                                                                                                                                                                                                                       |
| **근거** | Monimo는 서버 상태가 대부분이고 클라이언트 글로벌 상태는 세션(Auth)과 새로고침 트리거(refreshKey) 두 가지뿐이다. Zustand·Redux를 도입하면 보일러플레이트와 학습 비용이 MVP 규모에서 과도하다. React Query 도입도 검토했으나 커스텀 훅 16개로 이미 쿼리 추상화가 충분히 되어 있다. |

### 결정 7: 뷰포트 기준 — 데스크톱 고정 vs 반응형

|          | 내용                                                                                                                                                                                                                        |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **채택** | 데스크톱 고정 (기준 1440px, 최소 1100px)                                                                                                                                                                                    |
| **버림** | 모바일 퍼스트 반응형                                                                                                                                                                                                        |
| **근거** | 가계부는 월말 정산, 내역 확인 등 데이터 밀도가 높은 작업이 많다. 테이블, 필터, 슬라이드 패널 레이아웃은 작은 화면에서 UX 손실이 크다. 모바일 반응형은 v2에서 별도 시간을 들여 제대로 처리한다. MVP에서는 완성도에 집중한다. |

## 5. 기술 스택 & 아키텍처

### 기술 스택

| 역할      | 기술                                     | 선택 이유                                          |
| --------- | ---------------------------------------- | -------------------------------------------------- |
| UI        | React 18 + Vite 6                        | 생태계 성숙, Vite의 빠른 HMR                       |
| 스타일링  | Tailwind CSS 4                           | CSS 변수 기반 테마, 클래스 조합으로 일관성 유지    |
| 라우팅    | React Router 6                           | SPA 표준, 중첩 라우트 지원                         |
| 차트      | Recharts 2                               | React 친화적, 커스터마이징 용이                    |
| 백엔드/DB | Supabase                                 | Auth + PostgreSQL + RLS를 원스톱 제공, 설정 최소화 |
| 폰트      | Pretendard (한글), JetBrains Mono (숫자) | CDN 로드, 한국어 가독성 + 숫자 정렬                |
| 배포      | Vercel                                   | GitHub 연동 자동 배포, 무료 티어                   |

### DB 스키마 (6개 테이블)

```
auth.users (Supabase 관리)
    ├── profiles        사용자 표시 이름, 월 예산
    ├── accounts        계좌 (name, type, color, initial_balance, is_active)
    ├── categories      카테고리 (user_id=NULL이면 공용 프리셋)
    ├── transactions    거래 (amount, type, category_id, account_id, date)
    ├── transfers       이체 (from_account_id, to_account_id, amount, date)
    └── budgets         예산 (category_id, amount, month[YYYY-MM])
```

모든 테이블에 RLS 적용: `SELECT / INSERT / UPDATE / DELETE` 모두 `user_id = auth.uid()` 조건.  
카테고리 프리셋(`user_id IS NULL`)은 SELECT만 전체 허용.

### 프론트엔드 구조

```
src/
├── App.jsx                  라우팅 (BrowserRouter + PrivateRoute)
├── contexts/                AuthContext, LedgerRefreshContext
├── hooks/                   Supabase 쿼리 추상화 (16개 커스텀 훅)
├── pages/                   LandingPage, LoginPage, SignupPage,
│                            DashboardPage, LedgerPage, BudgetPage, AccountsPage
├── components/
│   ├── ui/                  Modal (범용)
│   ├── layout/              AppLayout, AppHeader, Sidebar, AuthLayout
│   ├── transactions/        TransactionFormModal, TransactionDetailPanel
│   └── accounts/            AccountFormModal, AccountDetailPanel
├── lib/supabase.js          Supabase 클라이언트 초기화
└── utils/                   accountColors.js, accountTypes.js
```

**훅 분류 (16개):**

- 인증: useLogin, useSignup
- 계좌: useAccounts, useAccountsWithBalance, useAccountDetail, useCreateAccount, useUpdateAccount, useDeleteAccount
- 거래: useTransactions, useCreateTransaction, useUpdateTransaction, useDeleteTransaction
- 이체: useTransfers, useCreateTransfer
- 카테고리: useCategories
- 예산: useMonthBudget

## 6. 비기능 요구사항

### 보안

- Supabase RLS: 모든 DB 쿼리에 자동으로 `user_id = auth.uid()` 필터 적용
- JWT 자동 포함: Supabase 클라이언트가 요청마다 Authorization 헤더 처리
- 이메일 인증 필수: 미인증 계정은 로그인 불가 (UX 레벨 차단)
- 환경 변수: Supabase URL/Key는 `.env.local` + Vercel 환경 변수로 관리

### 성능

- 월별 단위 조회: 전체 데이터 조회 없이 선택된 월만 fetch
- 클라이언트 잔액 계산: DB aggregate 함수 대신 JS로 계산 (쿼리 단순화)
- `refreshKey` 패턴: 거래 변경 시 필요한 컴포넌트만 리렌더링

### 지원 환경

- 브라우저: Chrome, Safari, Edge 최신 버전
- 뷰포트: 최소 1100px (MVP), 최적 1440px
- 모바일: v2에서 대응 예정

### 알려진 이슈

- 숨겨진 모달(CSS display:none 없이 visibility 처리)에 Tab 키로 포커스 가능 → 접근성 이슈. pre-existing 문제로 v2에서 수정 예정.

## 8. 범위 밖 (v1 제외)

다음은 v1에서 **의도적으로 제외**한 항목이다.

- **모바일 앱 / 네이티브 앱**: 웹 앱으로 먼저 완성, 모바일은 v2 반응형 후 검토
- **외부 계좌 자동 연동**: 뱅킹 API 연동은 인증·보안 복잡도가 높아 MVP 범위 초과
- **Google OAuth**: 이메일 인증으로 충분, OAuth는 v2에서 추가
- **고정 지출 자동화**: 수동 입력 UX 완성 후 자동화 기능 추가
- **CSV/엑셀 내보내기**: 핵심 가치(보기 쉬운 요약)와 직결되지 않음
- **다크 모드**: 디자인 시스템 안정화 이후 적용
- **팀 공유 / 가족 가계부**: 멀티유저 지원이지만 개인 단위 사용이 MVP
